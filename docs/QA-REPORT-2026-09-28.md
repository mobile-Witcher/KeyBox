### 断言 3 · R14 `kbAdminDeleteUserData` 六项护栏
**结论：通过。**
- 证据（行为，`step8CloudFunctions.test.ts`，加载的是**云函数真实源码**）：
  - ① 只收一个 `uid`：管理员但 `event={}` 或 `event.uid="   "` → `MISSING_UID` 且**不发 DELETE**；正常路径 DELETE 查询恰为 `{owner_id:"eq.<目标>"}`。
  - ② 身份取自服务端：`getCaller` 返回非管理员、`event.uid` 伪造成管理员 → `NOT_ADMIN`；自检查询用的是 **callerUid**（`eq.attacker-uid`），且序列化调用记录中**不含** `real-admin-uid`。
  - ③ 先自检：非管理员时**除 GET 自检外无任何写操作**。
  - ④ `return=minimal`、绝不 representation：DELETE 的 `prefer==="return=minimal"`；**所有请求** `prefer` 均不含 `representation`。静态：`kbAdminDeleteUserData/index.js` 去注释后**无** `return=representation`、**无** `RETURNING`。
  - ⑤ 返回体只含 `{deletedCount}`：`Object.keys(res.data) === ["deletedCount"]`，差值正确（5→2 得 3；1→4 得 0 不为负）。响应体不含 `payload`/`KB1:`。
  - ⑥ 用户软删：`PATCH kb_users` 且 `body==={status:"deleted"}`、`query==={uid:"eq.<目标>"}`；**无** 对 `kb_users` 的物理 DELETE。
- 证据（源码）：`cloudfunctions/kbAdminDeleteUserData/index.js:40-67`。
- 边界补充：
  - "计数两次均按 owner_id=目标 收口"（无跨用户泄漏面）。
  - 底层抛错 → `fail(message)`，不抛裸异常。
  - **"删除后残留孤儿行"**：DELETE 直接按 `owner_id` **物理删除**该用户全部 `kb_secrets`，故**不留孤儿行**；软删后 `kb_admin_user_list()` 的 `item_count` 由 `kb_secrets` 左连接计数得到，删除后自然归零。
- 影响与建议：无阻塞项；`deletedCount` 的非原子性见 Q3。

## 新发现问题（本步新增，按严重度）

### Q1【中】管理员可删除**自己那一行**的数据 → 单管理员场景**永久锁死**
- 现象：`AdminPage.tsx` 的用户表格中，"停用/启用"按钮对**自己那一行**被替换为提示"不能停用自己…"（`:360-362`），但紧随其后的 **"删除数据"按钮对每一行无条件渲染**（`:372-379`），**包括自己**。管理员确认后将调用 R14 → 自己 `kb_users.status='deleted'`。
- 根因链（不可逆）：软删后 `kbLogin` 因 `status!='active'` **拒登**；而 `kbInitAdmin` 因 `kb_users` **非空**拒绝二次初始化 → **再也无法创建/恢复管理员**。架构把"逃生口"寄托在"另一个管理员可恢复"，**单管理员（20 人自建场景常见）没有另一个管理员**，此路不通。
- 证据：`src/pages/AdminPage.tsx:360-379`；`cloudfunctions/kbAdminDeleteUserData/index.js:58-62`（软删自己）；`cloudfunctions/kbRegister` 与 `kbInitAdmin` 的既有口径（非空拒绝）。
- 最小修复建议（二选一，改动极小）：
  1. 与"停用自己"一致，对 `isSelf` 行**不渲染"删除数据"按钮**（或置灰 + 提示"请用另一个管理员操作"）；或
  2. 在 `kbAdminDeleteUserData` 内增加自检：`if (targetUid === callerUid) return fail("CANNOT_DELETE_SELF")`（服务端兜底，防绕过 UI）。建议**两者都做**（UI 防呆 + 服务端兜底）。
- 备注：`us2/us4` 并未要求"管理员不能删自己"，故这是设计与实现的**防呆不对称**（停用被防了、删除没防）；是否修由 team-lead 决定。

### Q2【低】`GRANT UPDATE(status)` 无取值约束，直连可写入 `'deleted'` 绕过 R14 的两步
- 现象：R13 直连 `update({status})` 的列级授权**不限制取值**。前端类型只开放 `active|disabled`，但一个被改的前端/未来 bug 可直连写 `status='deleted'`：**只软删用户、不清 `kb_secrets`** → 该用户密文成为"孤儿密文"（因列表按 `status<>'deleted'` 过滤而不可见），并已释放名额。
- 影响：仅管理员可达；不泄露明文（密文仍是密文），但留下不可见残留密文与"名额已释放但数据仍在"的不一致。
- 最小修复建议：给 `kb_users` 的更新策略加取值约束，或增列级 `CHECK`：策略 `WITH CHECK ( is_admin() AND status IN ('active','disabled') )`（`'deleted'` 只允许服务端写）。低优先。

### Q3【低】`deletedCount` 用 before/after 两次 `pgCount` 计算，**非原子**
- 现象：`kbAdminDeleteUserData` 先计数、DELETE、再计数，差值即 `deletedCount`。若在两次计数之间该用户有并发新增（请求走的是 `service_role` 之外的手段，概率极低），返回值会偏差。**删除范围本身正确**（始终按 `owner_id`），仅影响**展示数字**。
- 最小修复建议（保留"绝不 RETURNING 内容"原则）：改用 PostgREST 的 `Prefer: count=exact` 让 DELETE 直接回 `Content-Range` 给出受影响行数，一次请求拿到精确计数、仍不返回任何行内容。低优先。

## 我判断**最可能在生产上出事**的一条

**Q1 —— 单管理员误点"删除数据"删掉自己，导致管理能力永久锁死且不可恢复。**
理由：其余问题均为"低/展示层/需管理员刻意绕过"，而 Q1 的触发路径是**界面上就摆着的一个红色按钮 + 一个确认框**，后果是**不可逆**（云端无管理员自救入口）；20 人自建场景**单管理员是常态**，"另一个管理员可恢复"的逃生口常常不存在。修复成本极低（隐藏自己行的删除按钮 + 服务端加一条 `CANNOT_DELETE_SELF` 自检），性价比最高，建议优先处理。
