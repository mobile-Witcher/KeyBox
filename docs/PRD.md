# KeyBox 产品需求文档（PRD）

> 读者说明：本文面向零代码基础的项目所有者。专业术语首次出现时用括号补一句白话解释（≤15 字）。
>
> 术语速查：
> - **主密码**：本地加密用的最高密码，云端没有。
> - **派生密钥**（KDF）：由主密码算出的一把钥匙。
> - **端到端加密**：只在本机加解密，云端只见密文。
> - **安全规则**：云数据库上的门禁条件。
> - **云函数**：跑在云端的后端代码。
> - **归属标记**：每条记录上写明"这是谁的"。
> - **邀请码**：一次性开户凭证。
> - **遮掩**：默认把密钥显示成圆点。
> - **登录票据**：登录成功后拿到的凭证。
> - **恢复码**：忘了主密码时的自救码。
> - **备份文件**：导出到本机的加密副本。
>
> **⚠️ 需求变更（2026-09-29）：登录方式改为「手机号验证码」**
> 原 R01/R04/R05 写的是"用户名 + 登录密码"由云函数校验并签发登录票据；实测该方案在当前环境不可用
> （平台侧自定义登录密钥无法生效，服务端恒报"私钥已过期或私钥不存在"）。现已改为**平台原生手机号验证码登录**：
> - **登录**：手机号 + 短信验证码（首次登录自动创建账号，无需注册表单）
> - **开户**：管理员发邀请码 → 用户手机号登录后填邀请码 + 自设主密码完成激活（邀请码一次性、仅限 20 人）
> - **主密码**：不变——只在你自己设备上加密数据，云端没有副本；遗忘时用**恢复码**自救
> - 因此"用户名 / 登录密码"这两项**已从产品中去掉**：不再需要记两个密码，也就不会再出现"忘了账号密码"的死局
> 上表术语中的「登录票据」在新方案里由平台直接签发，业务侧不再自建。
> - **RLS**：数据库按行判断该不该给你。

## 1. 一句话结论

**KeyBox 是给 20 人以内的团队用的密钥保管箱：每人用自己的主密码（本地加密密码）在本机加密自己的 API 网址与密钥，云端和管理员都只能看到密文（乱码）。**

## 2. 产品目标（3 条，可验证）

| # | 目标 | 验证方式 |
|---|------|----------|
| G1 | 云端不出现任何明文密钥 | 直接在 CloudBase（腾讯云开发）后台打开数据表，全字段为密文；管理员账号登录后也无任何可读明文字段 |
| G2 | 用户之间数据互不可见 | 用 A 账号调用读取接口查 B 的记录，返回空或报错；改前端代码重发请求同样失败 |
| G3 | 开户全自助、管理员零接触明文 | 管理员只发邀请码（一次性开户凭证），对方自助完成；管理员全程无需也无法得知对方主密码与密钥 |

## 3. 用户故事（9 条）

| 编号 | 角色 | 用户故事 |
|------|------|----------|
| US1 | 管理员 | 作为管理员，我要生成一次性邀请码，这样才能把开户交给对方自己完成、我不接触他的密码 |
| US2 | 管理员 | 作为管理员，我要看用户列表（用户名、条目数、状态），这样才知道谁开了户、谁还空着 |
| US3 | 管理员 | 作为管理员，我要停用某个账号，这样对方被停后立刻登不上、但其数据还在 |
| US4 | 管理员 | 作为管理员，我要能删除某个用户的全部数据，这样对方彻底退出后不留残留 |
| US5 | 终端用户 | 作为新用户，我要用邀请码自助填用户名、登录密码、主密码完成开户，这样管理员看不到我设的任何密码 |
| US6 | 终端用户 | 作为用户，我要用登录密码登录、再用主密码解锁本机密钥，这样两层分开、丢一层不至于全丢 |
| US7 | 终端用户 | 作为用户，我要存 API 网址 + 密钥并打标签、按关键词搜索，这样几十条密钥也找得到 |
| US8 | 终端用户 | 作为用户，我要密钥默认显示为圆点、点击才显示、一键复制，这样旁人路过屏幕看不到 |
| US9 | 终端用户 | 作为用户，我怕忘了主密码，我要有一串**自己保管**的恢复码（一次性自救码），这样不至于把全部 API 密钥一次性丢光 |

## 4. 需求池（26 条；P0 = 没有就不能用）

表头固定：编号｜需求描述｜优先级｜验收标准｜因为什么才必须有这条

| 编号 | 需求描述 | 优先级 | 验收标准 | 因为什么才必须有这条 |
|------|----------|--------|----------|----------------------|
| R01 | 首个管理员账号在项目初始化时由所有者手动输入（用户名+登录密码+主密码） | P0 | 首次启动时出现初始化页；写入后该账号被标记为管理员；此后不再出现该页 | 因为之后所有账号都走邀请码，没有第一个人就无法发出第一个码 |
| R02 | 管理员生成邀请码，在**云函数**（跑在云端的后端代码）内写入 | P0 | 生成后返回一个一次性码；码值带随机性不可猜测 | 因为放在前端生成等于任何人都能自己造码开户 |
| R03 | 注册时邀请码是否有效，由云函数校验并原子占用（一次性失效） | P0 | 用过一次后立即失效；同一码并发提交只有一次成功 | 因为前端判定可以被改代码绕过，码会被无限复用 |
| R04 | 自助注册：填邀请码+用户名+登录密码+主密码；**登录票据（登录成功的凭证）由云函数在校验邀请码后签发** | P0 | 提交后账号可登录；主密码不上传任何字段；用户侧体验仍是填四项 | 因为开户必须自助，管理员才不会接触用户密码；且平台不允许纯用户名密码注册，票据只能由云函数签发 |
| R05 | 登录：登录密码校验在云端，云端只认身份、不认主密码 | P0 | 登录成功返回会话凭证；请求中不含主密码 | 因为主密码一旦上传，端到端加密（只在本机加解密）就名存实亡 |
| R06 | 主密码在本机经 KDF（把密码变密钥的算法）+ 随机盐值派生密钥 | P0 | 同一主密码在不同账号派生结果不同；派生只在本机内存 | 因为直接用主密码当密钥，弱密码会被撞库暴力破解 |
| R07 | 密钥内容本机加密后才上传，云端只存密文 | P0 | 抓包与查库均为密文；断网时本机仍可解密已缓存内容 | 因为云端一旦有明文，运营方与管理员都能读到 |
| R08 | 每条记录写入归属标记（记录上写明"这是谁的"） | P0 | 每条记录含 owner 字段，创建时由云函数按会话身份写入，前端传值一律忽略 | 因为不标记归属，安全规则（云数据库门禁）就无从判断该不该放行 |
| R09 | 安全规则：用户只能读写自己的记录 | P0 | A 查 B 的记录返回空；改前端换 owner 重发仍被拒 | 因为只靠前端过滤等于把门锁装在门帘上，改代码即穿 |
| R10 | 安全规则：管理员可删除任意记录，但不可读取其密文字段 | P0 | 管理员调用读接口取他人密文返回空；删除成功；**任何响应体中不得出现密文字段** | 因为管理员职责是管人不是看内容，权限必须写死在门禁里 |
| R11 | "是否管理员"由云函数判定后返回标记 | P0 | 前端无任何本地 isAdmin 常量；篡改请求也无法获得管理员能力 | 因为前端判定可以被改代码绕过 |
| R12 | 管理员看用户列表：用户名、条目数、状态、注册时间 | P0 | 列表来自云函数聚合；**响应体中不得出现任何密文字段**（只返回用户名、条目数、状态、注册时间四项） | 因为管理员要管人，必须先看见有谁 |
| R13 | 管理员停用/启用账号 | P0 | 三个窗口分别验收：① 新登录被拒；② 云端访问在票据刷新间隔内失效（配置 15 分钟，**验收按 ≤30 分钟**，兜底 2 小时）；③ 客户端前台 60 秒内发现停用、立即登出并清空本机已解锁内容；启用后恢复；④ 管理员**改不了任何人的登录凭据**（列级授权只放开状态列，登录哈希不在放开范围内） | 因为人员离开时没有停用手断，只能删库，代价太大 |
| R14 | 管理员删除某用户全部数据 | P0 | 一键删除该用户所有记录；操作在云函数内二次校验管理员身份；**删除的响应体中不得出现任何密文字段**（禁止用 RETURNING 把内容带回来） | 因为这是唯一的清理手段，且必须防止被冒用 |
| R15 | 用户对自己的密钥增删改查（站点名、网址、密钥、备注） | P0 | 增改后重新加密上传；删除即时生效；列表本机解密展示 | 因为这是产品存在的唯一理由 |
| R16 | 密钥默认遮掩（显示为圆点），点击显示，一键复制 | P0 | 进入页面默认圆点；点击后明文；复制按钮不经过任何上传 | 因为屏幕被旁人看到的概率远高于被黑客攻击 |
| R17 | 主密码与密钥明文永不出本机（不写日志、不报错回传、不进崩溃上报） | P0 | 全局检索代码中无明文上传路径；日志中脱敏 | 因为只要有一次外泄，双层加密的整体承诺即作废 |
| R18 | 标签：给密钥打标签并按标签筛选 | P1 | 可新建/重命名/删除标签；一条密钥可多标签 | 因为超过十条密钥后，无分类就只能靠人肉翻 |
| R19 | 搜索：按站点名/网址/标签关键词本地检索 | P1 | 输入即时过滤；不把关键词发往云端 | 因为关键词发云端等于泄露用户有哪些站点 |
| R20 | 桌面端 Tauri 2（把网页打包成 exe 的工具）打包 Windows exe | P1 | 仓库含打包配置；本地可产出可安装 exe | 因为终端用户不会装 Node 跑网页，必须有 exe |
| R21 | 修改主密码：本机重新加密全部记录后覆盖上传 | P1 | 改完后旧主密码失效；中途失败不留下半旧半新 | 因为主密码一旦疑似泄露，用户需要有自救手段 |
| R22 | 人数上限 20：达到上限后云函数拒绝再开户 | P1 | 第 21 个注册被拒并提示联系管理员 | 因为不做分页与配额，必须显式封顶防止表失控 |
| R23 | 安卓端 Capacitor（把网页打包成 apk 的工具）+ GitHub Actions（自动打包流水线）产出 apk | P1 | 仓库含工作流；推送标签后可下载 apk 产物 | 因为手机端是次要场景，但所有者希望一并开源可复现 |
| R24 | 夜间模式手动切换 | P2 | 右上角按钮切换；选择被记住 | 因为只在深色环境下有用，不影响主流程 |
| R25 | 复制后提示"N 秒后自动清空剪贴板"倒计时 | P2 | 复制后出现倒计时提示 | 属于体验补强，缺失不影响可用性 |
| R26 | 用户规模达到 20 人时，管理员后台顶部提示"已达上限" | P2 | 满员时出现提示条 | 属于提醒，缺失时 R22 已可阻断 |
| R27 | 开源部署可复现：提供一键下发脚本（建集合 + 安全规则 + 角色策略）+ 手工兜底清单，README 写清部署步骤。**负责人：许清楚** | P1 | 新环境照 README 可完成部署；脚本幂等（重复执行不报错、不重复建）；脚本跑不通时，手工清单能独立完成 | 因为项目要全量开源，零基础部署者若卡在控制台配置，等于开源了但没人装得上 |
| R28 | 恢复码（一次性自救码）：用户设好主密码后可生成，**只显示一次**，由用户自行抄存；遗忘主密码时用它在本机解开数据并**强制重设主密码** | P1 | ① 恢复码只显示一次，关闭后无法再次查看；② 恢复码不出现在任何日志、请求体、崩溃上报中；③ 用恢复码能解开本机数据；④ 恢复成功后强制重设主密码，旧主密码作废；⑤ 生成页与遗失场景下界面提前警示"丢了就等于没开" | 因为平台侧找回在技术上不可能、且会破坏零知识（服务端不掌握任何能解开的钥匙），但让用户完全没有自救手段不符合实际使用场景 |
| R29 | 加密备份导出：用户可导出一份加密备份文件到本地，内含全部记录密文与密钥参数；换设备时可用主密码在本机还原 | P1 | ① 导出文件全为密文，用文本编辑器打开无明文；② 换设备用主密码导入后数据与导出时一致；③ 导入还原**不依赖云端在线**；④ 导出与导入全程不上传主密码 | 因为恢复码解决"忘了主密码"，备份解决"设备丢了/坏了"这一类同样会导致全部密钥一次性丢失的场景，两者不可互相替代 |

### 产品红线（与 R28 / R29 相关，不可省略）

| # | 红线 | 落到哪里 |
|---|------|----------|
| L1 | **恢复码由用户自己保管，丢了就等于没开** | 这句话必须出现在**生成恢复码的界面文案**里，不能只藏在 FAQ 或 README |
| L2 | **主密码 + 恢复码 + 备份文件三者全丢 = 永久不可恢复** | 必须在 README 第 3 节「代价」里明说 |
| L3 | 服务端不参与、不知晓恢复过程 | 不做密保问题、不做邮件重置；恢复与导入全部在本机完成 |
| L4 | **管理员即便拿到用户的恢复码密文也解不开** | 恢复码不在云端存明文；管理员侧无任何恢复入口 |

### 实现备注（来自架构核实，影响验收，请照此验收）

| 涉及 | 备注 |
|------|------|
| 全局 | **环境已实测为 PostgreSQL 模式**（`queryEnv` 返回 `RuntimeMode="postgresql"`），不是文档型数据库。故 PRD 中的"安全规则"实际落地为 **PG 行级安全策略（RLS，数据库按行判断该不该把这条给你）**。两个后果：① R09 的"A 查 B 返回空"正是 RLS 最自然的表现（**自动过滤而非报错**），验收措辞无需改动；② R10 的「不可读」与「可删」**都由数据库策略保证，不需要绕过**。原因是 PG 的 `USING` **按操作独立生效**：DELETE 有自己独立的 `FOR DELETE` 策略，**不要求先通过 SELECT 策略的可见性**（我上一版判断"删也要先看得见"是错的，已更正）。故"能删但读不到"可用两条策略直接表达：SELECT 策略只放 `owner = 本人`，DELETE 策略放 `is_admin()`（**普通函数，不绕过门禁**，故不需要平台支持任何特殊数据库能力） |
| R10 / R13 / R14 | **由数据库策略保证，无任何平台前提**：① **R10 / R14 可删不可读**——管理员用自己的会话删，由 DELETE 策略放行，**全程不接触内容**；② **R13 停用**——用**列级授权只放开 status 一列**，管理员能改状态但**改不了任何人的登录凭据**（登录哈希不在放开范围内）。三条都依赖一个"是不是管理员"的判定函数，而**该函数是普通函数、不绕过门禁**（它只需读调用者自己那一行，而"读自己"本来就被允许），因此**不需要平台支持任何特殊数据库能力** |
| R12（唯一的回退面） | **仅 R12 存在回退可能**：用户列表与条目数必须跨用户读取，是全项目唯一需要读**他人**行的功能，无法用"只读自己"的策略覆盖，只能依赖一个**绕过权限的聚合函数**（只返回"用户+条数"，永不返回内容）。**⚠ 未实测**：该函数能否在平台创建、属主是否与表同属主。**若不支持，只有 R12 回退**为代码保证，**R10 / R13 / R14 不受影响** |
| R10 / R12 / R13 / R14（给项目所有者的一句话） | 管理员的四个动作里，**三个（删除数据、停用、启用）由数据库门禁直接保证，且不需要平台支持任何特殊能力**；**只剩一个（用户列表）**需要平台支持一项数据库能力，**不支持也只是它自己回退**，不影响另外三个。**两种情况下都保留同一道机器防线**：管理员类云函数**返回字段白名单**（禁止 `select *`；删除时禁止把内容带回来）+ 对云函数目录做**正则自动扫描**的 CI 检查。R10 / R12 / R14 的验收已各加一条可勾选项：**响应体中不得出现任何密文字段**（无论走哪条路径都要验收）。**另有第二个前提不在管理动作里**：开户与登录链路（R01 / R04 / R05 / R11 / R21）需要云函数能持服务端凭据读敏感列，**这个前提与上面那个相互独立**，详见 R01 / R04 / R05 / R11 / R21 备注行 |
| R01 / R04 / R05 / R11 / R21 | **⚠ 开户与登录这条链路另有一个平台前提，别漏**：管理员的四个动作虽已不依赖它，但**开户与登录本身仍然需要**——建首个管理员、注册、登录、查自己角色、改主密码这几个云函数，都必须**持服务端凭据**去读"登录哈希、密钥参数"这几列；而这几列是为了屏蔽敏感信息**刻意不对客户端开放**的，所以客户端直连拿不到，只能由服务端读。**若云函数在 PG 下拿不到服务端凭据，R01 / R04 / R05 / R11 / R21 五个 P0 全部做不了**（不是回退，是直接不可用）。此前提与管理动作那条相互独立。**✅ 已于只读体检实测：服务端角色存在且具备绕过行级策略的属性，故本前提当前成立**（维持"未触发"，非"已闭环"）。**定性保留作万一**：这几列刻意未对客户端开放（放开等于允许离线枚举登录哈希），**没有任何客户端兜底**，故一旦该路径失效，这五个是"直接不可用"而非"回退" |
| R13（可勾选测法） | 拿**管理员会话**改他人 `login_hash` → **应被拒**；改他人 `status` → **应成功**。**顺带测一条**：拿**普通用户会话**改**自己**的 `status` → **应被拒**（更新策略要求"是管理员"）。因为 PG 的列级更新权限是按语句里实际涉及的列逐列检查的，不是整表放行 |
| R04 | 平台（CloudBase）不允许仅用"用户名+密码"直接注册，必须经邮箱或短信验证。**因此不接邮箱手机**，改用自建账号表存登录密码哈希，由云函数在校验邀请码后签发自定义登录票据。用户侧仍是填四项，体验不变 |
| R13 | 停用的"失效"要分**两个窗口**验收，二者互不可替代：① **云端窗口**（还能不能拉到新密文）：票据刷新间隔可自行配置，目标 15 分钟，刷新时服务端发现停用即拒发新票据，兜底为票据自然过期 2 小时。**验收按 ≤30 分钟**，架构实测校准后再收紧到 15 分钟；② **本机窗口**（还能不能看已解密的内容）：云端吊销管不到，因为内容已在本机内存里，只能靠客户端前台每 60 秒查一次状态，发现停用立即登出 + 清空内存主密钥 + 锁本地缓存，**验收按 ≤1 分钟**。此窗口不依赖平台是否有吊销接口。**残余风险已评估为可接受、不升级为阻塞项**：即使停用后会话仍存活，云端门禁（安全规则）依旧只允许该账号读**自己**的记录，读不到任何他人的内容；叠加本机 ≤1 分钟的轮询清理后，残余风险仅为"他还能看自己已解锁的内容一小会儿"。20 人自用场景下接受此风险。**两项未实测**：设成 15 分钟后是否真按该间隔回调取票函数；刷新被拒时当前 access_token 是立即作废还是继续活到自然过期（若为后者，压短 refresh 无效，云端窗口实际仍是 2 小时）。故 PRD 不提前收紧到 15 分钟 |
| R04 / R09 | 已知官方归档问题：自定义票据登录成功但读库报 UNAUTHORIZED，根因是"新用户默认角色为外部用户"，需在控制台给用户角色配资源策略。**未做这一步会表现为"能登录但什么都读不到"**，易被误判为 R09 安全规则写错。实施第 2 步必须先验证此项，再验 R09。**⚠ 适用范围**：该坑出自**文档型数据库**的权限语境；本环境实测为 PG，角色模型为"未登录 / 已登录 / 服务端"三种，**此坑未必适用**。架构侧已把待核实项改为"自定义登录的会话是否确实落在已登录角色"。排查时勿照文档型数据库那套语境找，先确认会话角色归属 |
| R04 / R27 | 建表与权限策略**均可脚本下发**（已核实存在 createRole / addRolePolicies / updateResourcePermission 及 CLI `tcb policy`），理论上不必手工点控制台。**但最大一项未查到**：PG 模式下**云函数怎么连库、能否拿到绕过行级权限的服务端凭据**——这决定了云函数能否正常聚合用户列表与删除数据。**未实测清楚前，README 第 7 节一律按"含手工步骤"写全**，架构确认后再逐条删。另 `addRolePolicies` 的 policies 详情对象结构未查到，同样存在脚本化不了的可能。**先写全再删，比先省事后补洞安全** |
